# Native distribution preview

Day 14 packages `foresee-semantics` (check/build compiler) and `foresee-lsp` (stdio language server). These binaries need neither Python nor Cargo at runtime. They compile the supported language subset; effect execution remains in the Python runtime.

## Download and use

Open the repository's **Actions > Verify** run for the desired commit and download `native-ubuntu-24.04` or `native-macos-14`. Unzip the GitHub artifact wrapper. It contains a `.tar.gz` archive and adjacent `.sha256` file. Select the archive matching your machine:

| Runner | Target | Scope |
| --- | --- | --- |
| Ubuntu 24.04 x86-64 | `x86_64-unknown-linux-gnu` | Tested on Ubuntu 24.04; glibc/system libraries required |
| macOS 14 Apple Silicon | `aarch64-apple-darwin` | Tested on macOS 14 ARM64; macOS system libraries required |

Older operating systems, Intel Macs, Linux ARM64, Windows, and static/musl builds are not validated. These are unsigned CI previews, not a published v0.2 release. There is no installer or automatic PATH modification.

Verify the adjacent checksum with `sha256sum -c ARCHIVE.tar.gz.sha256` on Linux or `shasum -a 256 -c ARCHIVE.tar.gz.sha256` on macOS. Extract into an empty directory, then run:

```sh
./bin/foresee-semantics check examples/repair.fore
./bin/foresee-semantics build examples/repair.fore -o repair.json
./bin/foresee-lsp
```

The language server waits for an editor's framed stdio messages. Configure an LSP-capable editor to launch its absolute path; no editor extension is included. The build output must not already exist. Compare it structurally with `examples/repair.ir.json`, generated by the reference Python compiler.

## Contents and provenance

- Two release-mode executables under `bin/`.
- `examples/repair.fore` and its complete reference IR, including program digest.
- `manifest.json` with compiler version, source commit, dirty-worktree flag, host target, toolchain, UTC build timestamp, and SHA-256 hashes for every other payload file.
- `sbom.spdx.json`, an SPDX 2.3 inventory derived from locked Cargo metadata and Cargo.lock. It includes workspace crates, transitive dependencies, build dependencies, declared licenses, registry package checksums, and dependency relationships.
- This guide, plus an adjacent checksum of the whole archive.

The SBOM inventories Cargo packages, not exact linked code, Rust standard-library contents, or system libraries. `NOASSERTION` records unknown or unreviewed licensing. This repository currently has no project license declaration. Dependency license metadata does not grant a license to project code. The SPDX metadata's CC0 data license applies only to the inventory. See the [SPDX document fields](https://spdx.github.io/spdx-spec/v2.3.1/document-creation-information/) and [package fields](https://spdx.github.io/spdx-spec/v2.3.1/package-information/).

Checksums detect corruption, not publisher authenticity. Use artifacts from the intended repository/run/commit. The verifier executes the archive's binaries, so use it only for trusted artifacts.

## Build and verify

From a checkout with the pinned Rust toolchain and Python 3.11+:

```sh
python tools/package_native.py
python tools/verify_native.py release-dist/native/*.tar.gz
```

Packaging explicitly builds the host target with the locked release profile and reads binaries from Cargo's resolved target directory. Archive names include the crate version, commit prefix, and target. Local changes are disclosed in the manifest. CI builds from a clean checkout. Archive container metadata is normalized, but timestamps, document UUIDs, toolchains, and compiled bytes mean full reproducible builds are not claimed.

The verifier bounds archive size, rejects unexpected paths, links, duplicate members, missing files, and payload checksum mismatches before writing payload files. It checks the host target, extracts to a temporary directory outside the checkout, then runs check/build and a full LSP session with an empty PATH. The LSP test uses the archived sample. The emitted IR must match the packaged Python reference. CI performs this verification independently on both supported platforms before uploading archives. Python is needed for this verification harness, not for using the binaries.
